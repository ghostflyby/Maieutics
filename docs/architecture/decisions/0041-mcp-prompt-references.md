# ADR 0041: MCP Prompt References — the Selection Loop Generalized to Server-Defined Prompts

Status: Draft

Date: 2026-10-08

Related: ADR 0026 (resource plane, `mcp://` escape hatch), ADR 0039 (skill
discovery and selection), ADR 0032 (content-path stance), ADR 0040
(contribution framework — why prompts are NOT a kind),
`docs/mcp-prompt-interaction-design.md` (full design, v2 — revised through
a two-lens adversarial review),
`docs/web-frontend-protocol.md` ("Skill references")

## Context

The kernel consumes two of MCP's three product-facing primitives: tools
(invoked by the model) and resources (read through the resource plane). The
third — prompts — is absent: server-defined, user-invoked templates that
expand into conversation content. The skill selection loop (ADR 0039
interaction half) established the pattern for exactly this shape of
interaction: catalog endpoint → markdown-link reference in turn text →
build-time expansion with typed failures → editor boundary model. Prompts
are the same interaction with three real differences: identity is
server-scoped (not a global flat namespace), templates are parameterized,
and content is generated by a server round-trip at expansion time.

## Decision

1. **Prompts join the session view as a consumer face of the MCP adapter,
   not a contribution kind.** They ride server generations (tolerant
   `prompts/list` beside tools/resources — a failed or unsupported listing
   contributes an empty prompt list, never a failed connection;
   `PromptListChanged`-driven relist) and a per-server access primitive.
   No manifest surface, no fingerprint domain, no reconcile pass — ADR
   0040's framework is untouched.

2. **The reference grammar is a markdown link over a dedicated scheme:**
   `[text](mcp-prompt://<serverId>/<promptName>?<arguments>)`. The
   serverId segment is an **opaque token, deliberately not a valid generic
   URI authority** — the operative invariant is that a prompt reference
   never enters any generic URI parser: both sides parse on the literal
   `mcp-prompt://` prefix with their own regexes, and renderers treat the
   href as opaque. `mcp-prompt` is registered as an unallocatable reserved
   scheme (the `file` precedent). Prompt names use
   `^[a-zA-Z0-9][a-zA-Z0-9_-]{0,63}$` (the MCP spec's own example is
   snake_case); servers or prompts outside the referenceable charset
   (either segment) list with `referencable: false`. Arguments travel as
   percent-encoded URL query (the RFC 3986 unreserved set kept literal —
   TS encoders must additionally escape `!'()*`, which
   `encodeURIComponent` leaves raw and which would break the link form);
   argument names obey the same alphabet.

3. **Expansion is build-time, per-server, budgeted.** The kernel calls
   `McpServerGeneration.GetPromptAsync` (TryAcquire + the server's
   `RequestTimeout`) through a Configuration-owned accessor beside
   `GetResourceServers()` — the bulk lease path is wrong (no serverId
   addressing, wrong dependency direction, and it runs at profile
   acquisition, after turn build). Unknown server → typed
   `mcp_prompt_unknown`; retired/reconnecting/timeout →
   `mcp_prompt_unavailable` (message names the reason); argument
   validation against the declared set (missing required, extraneous,
   duplicate keys → `mcp_prompt_argument_invalid`, listing each missing
   argument's name and description — the stage-1 user's only argument
   discovery channel, so the failure is self-sufficient); a structurally
   unusable result → `mcp_prompt_result_invalid`. One shared per-turn
   reference-content budget (8 MiB, the skill budget generalized) covers
   skill bodies and prompt expansions in a fixed order (skills first, then
   prompts, each by first appearance — position in the cell does not
   reorder the budget); a single prompt's expansion is capped at 4 MiB
   (over-cap → the shared 413 budget failure; the transport buffers, so
   timeout and cap can fire in either order). Expansion dedupe keys on
   `(serverId, promptName, canonicalized query)` — same prompt with
   different arguments is different content. Server-side argument
   rejection (JSON-RPC -32602) maps to `mcp_prompt_argument_invalid`.

4. **Prompt messages are injected as user-side framed content with
   kernel-forged role framing, not as conversation turns.**
   `GetPromptResult.Messages` bridge via the SDK's `ToChatMessages()` and
   flatten to `TextContent` parts; the kernel writes a distinctive header
   line per message (role and ordinal) and escapes role-shaped leading
   text in the body, so template content cannot forge framing. Text blocks
   are kept; image, audio, and embedded-resource blocks are dropped with
   per-block diagnostics. Rationale: the content enters through the user's
   selection, the authoritative transcript must not gain assistant turns
   that never happened, and the framing preserves the template's speaker
   structure observably. **The revision seam is recorded honestly**: the
   genuine alternative is `AgentTurn` carrying non-committed pre-run
   messages (request messages already diverge from committed turns in
   `AgentSession`), an Agent-internal change — revisitable if assistant-
   structured templates measurably degrade under flattening.

5. **The editor interaction reuses the skill boundary model as ONE
   model.** Skill and prompt references share a single alternation
   grammar, a single mint/validate/encode pass, and the `$` trigger
   character (slash is already claimed by command completion; the catalog
   groups skills and per-server prompts in one list). Stage 2 inserts
   references only for referencable prompts without required arguments
   and shows argument declarations in the completion detail; parameterized
   prompts degrade to a hand-typeable hint until stage 3. **Stage 3's
   argument form is frontend-local** (rendered from the catalog's
   argument declarations, zero server round-trips): the `input.request`
   machinery is owned by the run lifecycle and would cancel instantly at
   selection time, where no run exists. Server-initiated elicitation
   during a build-time prompt request is answered cancel (the attribution
   coordinator keys on in-flight tool calls, which builds do not have —
   cross-session misattribution is the alternative).

## Consequences

- The selection loop pattern (catalog → link reference → build-time
  expansion → typed errors) is now instantiated twice; a third instance
  starts from the design doc's §1 table rather than from scratch.
- Reconnecting servers list no prompts, exactly like tools and resources
  (no generation-level last-known-good state is introduced); a frontend
  may keep its own cache with a state marker.
- The `skill_budget_exceeded` error becomes the shared reference-content
  budget failure; its name is kept for wire compatibility, its message
  text generalized, and the alias intent recorded in the error registry.
- `mcp_prompt_result_invalid` maps to 400, matching the repo's error
  taxonomy (no 5xx precedent; even `agent_provider_error` answers 400).
- Generic markdown renderers given the cell text may mishandle the opaque
  href — an accepted limitation (the reference's arbiter is the kernel
  grammar, not the renderer), noted in the protocol doc.
